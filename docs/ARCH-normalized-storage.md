# 저장 구조 정규화 검토 (H5d)

설계 문서만 작성하며 운영 DB 조회·마이그레이션·이중 쓰기는 실행하지 않았습니다. 감사 기록 보관 정책(H5c)은 사용자의 요청에 따라 보류 상태입니다.

## 현재 구조와 측정

WorkspaceData 전체를 로컬 JSON 파일 또는 workspaces 테이블의 JSONB 한 행으로 보관합니다. 쓰기는 전체 상태를 읽고 명령을 적용한 뒤 다시 직렬화합니다. 아래는 **2026-11-08 03:55 KST에 기존 격리 QA 파일을 읽기만 한 실측**이며 운영 데이터가 아닙니다. 최초 메모리 시드의 일부 필드만 제시했던 표를 모든 실제 최상위 필드 측정으로 보완했습니다.

- 입력: `.data/document-review-qa/workspace.json` (합성 QA와 앞선 수동 검증 데이터).
- 원본 파일 410,527B, 마지막 수정 `2026-11-08 03:05:07 KST`; 들여쓰기 없는 UTF-8 JSON은 288,003B.
- 원본 SHA256: `88b53b8e238dee63207f493db660c13fa44fcbc587241b2cd401ec2360f92ee2`. 두 번 실행 전후 동일하며 원본·DB·저장소를 쓰지 않았습니다.
- 측정 도구: `scripts/measure-workspace-growth.ts`. 입력 파일은 명시적으로 지정하며 환경 파일·저장소 초기화·네트워크 경로를 사용하지 않습니다.
- 결과: `.data/workspace-growth-2026-11-08.json`, 재실행 `.data/workspace-growth-repeat-2026-11-08.json`. 원본 필드 값이나 인적 사항은 출력하지 않고 크기·개수만 출력합니다.

## 명령 반복에 따른 증가량

각 시나리오는 위 파일의 독립적인 메모리 복사본에서 시작합니다. 실제 `executeCommand`로 본인 단위업무와 세부업무를 하나씩 준비하는 2개 명령을 먼저 실행했습니다. 준비 증가량 3,644B를 별도로 제외한 **291,647B**가 아래 모든 시나리오의 기준입니다. 같은 길이의 합성 제목·설명·요청 ID를 쓰고 명령 시각은 `2026-11-08T00:00:00Z`에서 1초씩 증가시켰습니다. 접근 가능한 활성 담당자와 같은 부서의 부서장·기존 편집 권한을 사용하며 권한·잠금을 임의 해제하지 않았습니다.

- `task.create`: 같은 본인 단위에 기본 4단계가 있는 새 세부업무를 한 개씩 생성합니다.
- `task.configure`: 같은 업무 설명의 고정 길이 변경 번호만 바꿉니다. 첫 수정은 수정 전 원본과 수정 후 버전을 함께 보존하므로 버전 2개가 늘고, 이후에는 1개씩 늘어납니다.
- `task.record`: 같은 업무에 날짜·설명·1,000원 금액의 합성 집행 한 건을 계속 추가하고 전체 집행 배열을 저장합니다. 변경마다 집행 배열의 전후 스냅샷이 보존됩니다.
- 모든 명령의 실제 감사 이벤트·요청 멱등성 기록·대상 revision 증가를 포함합니다. 현재 보관 정책(H5c) 보류 상태의 결과이며 배열을 인위적으로 채워 만든 추정치가 아닙니다.

100회 시점의 증가량을 저장 필드로 나누면 다음과 같습니다. 각각 감사 100건·요청 이력 100건이 늘었습니다.

| 명령 | tasks 증가 B | audit 증가 B | processedRequests 증가 B | revision 증가 B |
|---|---:|---:|---:|---:|
| task.create | 250,900 | 26,100 | 16,000 | 1 |
| task.configure | 245,403 | 28,394 | 16,000 | 1 |
| task.record | 1,047,150 | 32,492 | 16,000 | 1 |

이 고정 길이 입력에서는 새 업무·기준 변경의 증가는 대체로 선형입니다. 반면 집행 배열을 한 건씩 늘려 매번 저장하면 이전·이후 전체 배열을 반복 보존하므로 해당 기록 부분의 총량은 건수의 제곱에 비례해 커질 수 있습니다. 100회 집행 저장에서 증가한 1,095,643B 중 1,047,150B가 tasks 내부 기록입니다. 따라서 감사 이력만 별도 보관해도 이 증가 원인은 남습니다. **기록의 보존 의미를 바꾸지 않고 변경분 또는 별도 기록 테이블로 옮길지**가 정규화 설계의 우선 검토 대상입니다. 이번 측정에서는 기록 삭제·요약·보관 정책을 변경하지 않았습니다.

초기 QA compact 크기 288,003B가 일정하다고 가정해도 33명이 한 번씩 저장하면 약 9.50MB를 직렬화합니다. 위 집행 100회 시나리오의 최종 1,387,290B 상태에서는 같은 계산이 약 45.78MB입니다. 이는 요청별 전체 문서 직렬화의 크기 곱셈이며 동시 처리량·응답 지연·실제 DB/네트워크 전송량 측정은 아닙니다. 실제 성장률은 업무 설명·절차·첨부 메타데이터·기록 길이와 저장 빈도에 좌우되며 이 3개 합성 시나리오를 운영 성장 예측으로 일반화하지 않습니다.

검증: 2회 실행에서 모든 필드·시나리오·증가량이 동일했고 원본 SHA256도 같았습니다. 3시나리오 × (준비 2 + 반복 100) = 306개 명령을 실행당 메모리에서만 처리했습니다. 원본 QA 파일 쓰기·실제 DB·외부 API·환경 파일 열람 없이 수행했으며 표준 출력 결과만 별도 계측 JSON에 보관했습니다. 통합 타입 검사와 변경 파일 형식 검사도 통과했습니다.

## 대안

| 안 | 장점 | 제약 |
|---|---|---|
| 현재 문서 + 대상별 충돌·읽기 분리 | 작은 변경, 기존 권한·트랜잭션 재사용 | 쓰기 행 잠금·전체 직렬화는 계속 존재 |
| 부서별 문서 | 부서 간 쓰기 분리, 단계적 도입 용이 | 부서 간 공통업무·인계·평가의 원자성과 전역 조직 변경이 복잡 |
| 엔터티별 테이블 | 행별 잠금·부분 조회·이력 페이지화 가능 | 권한·마이그레이션·일관성·복구 검증 범위가 큼 |

권장안은 먼저 현재 구조에서 충돌 안내와 조회 잠금을 개선하고 실제 부하를 측정한 뒤, 지속적인 동시 사용이 확인되면 엔터티별 테이블로 전환하는 것입니다. 부서별 문서 분할을 중간 단계로 반드시 거치지는 않습니다.

## 목표 구조

tasks, task_versions, workflow_steps, runs, run_steps, run_notes, units, common_tasks, distributions, handovers, transfers, performances, score_plans, evaluations, notifications, audit_events, processed_requests로 저장 책임을 나눕니다. 원본 완료 결과와 평가 시점의 스냅샷은 불변 기록으로 보존합니다. 조직·사용자·기간·대상 ID에는 외래키와 필요한 인덱스를 둡니다. 감사 보존 기간·보관 위치는 정책 결정 후 확정합니다.

## 단계적 이관·롤백

1. 현재 명령 계약·권한 규칙·보존해야 할 스냅샷을 테스트로 고정합니다.
2. 새 스키마를 추가하고 기존 문서의 읽기 전용 변환을 dry-run하여 누락·중복·참조 오류를 보고합니다.
3. 동일 트랜잭션 또는 트랜잭셔널 outbox로 이중 쓰기합니다. 두 독립 쓰기의 성공을 가정하지 않습니다.
4. 새 조회 결과를 shadow read로 비교하고, 조직·업무 범위별로 읽기 플래그를 전환합니다.
5. 일정 기간 기존 문서를 유지합니다. 새 쓰기 내용을 기존 형식으로 복구할 경로가 검증된 동안만 읽기 플래그를 되돌리는 롤백이 안전합니다.
6. 감사·운영 정책 승인과 백업 복구 시험을 거친 후 이전 형식의 쓰기를 종료합니다. 구 문서 폐기는 별도 승인 대상입니다.

## 권한·검증 위험

canReadTask, 부서 범위, 업무대행 유효기간, 전임자의 성과 참고 파일, 평가 스냅샷 접근은 단일 task 소유자 검사로 대체할 수 없습니다. SQL WHERE 조건과 응용 계층 정책이 일치해야 하며, 다른 부서·후임·만료 대행자에 대한 음성 권한 테스트가 필요합니다. 집계·검색·내보내기에도 같은 범위를 적용합니다.

검증은 명령별 전후 동등성, 동시 편집 충돌, idempotency, 이중 쓰기 실패 복구, 시간 경계·인사이동, 대용량 이력 페이지화, 백업 복원으로 구성합니다. 운영 전에는 33명 이상의 합성 동시 요청으로 p50/p95 지연과 잠금 대기를 측정해야 합니다.

## 결정할 사항

감사 보존 정책, 요청 멱등성 기간, 예상 사용자·동시 쓰기량, 허용 중단 시간, 이중 쓰기 운영 기간, 복구 시점 목표와 책임자를 확정해야 합니다. 이 설계는 그 결정을 대신하지 않습니다.
