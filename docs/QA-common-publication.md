# 공통업무 작성·배포 승인 안내와 QA

기준일: 2026-11-05. 프로토타입의 공통업무 권한과 배포 흐름을 설명합니다. 구현 내용과 실제 검증 결과를 구분하며, 아래 검증 결과는 통합 점검 담당자가 기록합니다. 실제 Neon 데이터의 초기화나 운영 전환을 전제로 하지 않습니다.

## 구현한 기능

- 기존 **공통업무 · 지시사항** 메뉴를 유지합니다. 별도 **공통업무 담당** 권한은 폐지하고, **개인 담당자**의 표시 이름을 **업무 담당자**로 변경합니다.
- 업무를 작성할 수 있는 활성 구성원이 공통 세부업무 한 건을 만들고 대상 부서를 지정합니다. 작성 부서장의 승인 전에는 대상 부서에 배포하지 않습니다.
- 화면 상단의 **작성·배포 승인**에서 승인 대기, 반려, 요청·처리 이력을 확인합니다. 승인 요청에는 요청 당시 제목·설명·마감일·반복 주기·필수 절차·대상 부서 등이 보존됩니다.
- 작성 부서장이 상세 내용을 검토하여 승인하거나 사유를 적어 반려합니다. 승인 후 지정 부서의 부서 담당자가 기존 배부 흐름을 시작합니다.
- 최초 요청이 반려되면 작성자가 내용을 보완하여 재요청할 수 있습니다. 추가 대상 부서도 별도 승인을 거칩니다.
- 공통업무와 지시사항 모두 배포 승인을 거칩니다. 지시자·지시일자, 장·차관 지시사항의 기획팀 통합 관리, 월별 실적 등 기존 기능은 유지합니다.

## 5개 역할과 책임

| 역할 | 공통업무 작성·요청 | 승인·접수 후 역할 |
| --- | --- | --- |
| 업무 담당자 (`member`) | 공통 세부업무 작성, 본인이 작성한 반려 건 보완·재요청, 본인 업무의 추가 대상 부서 승인 요청 | 배정받은 업무를 내 단위업무에 등록하고 수행 기록·결과 입력 |
| 팀장 (`lead`) | 일반 업무 작성자와 같은 작성·재요청 가능 | 부서 담당자가 배부한 팀 업무의 업무 담당자 지정 |
| 부서 담당자 (`manager`) | 일반 업무 작성자와 같은 작성·재요청 가능, 작성 부서의 승인 요청 현황 확인 | 지정 부서로 접수된 업무를 팀에 배부, 부서 진행 현황 확인 |
| 부서장 (`head`) | 새 공통업무 작성 버튼은 제공하지 않음 | 작성 부서의 다른 구성원이 요청한 신규·추가 배포를 승인·반려, 부서 현황 확인 |
| 관리자 (`admin`) | 작성·조회·반려 건 보완 등 관리 지원 | 전체 현황 확인과 기존 관리 범위의 배정 지원. 작성 부서장의 승인을 대신하지 않음 |

작성과 승인은 활성 상태 및 계정 만료 여부를 검사합니다. 별도 공통업무 권한을 켜거나 공통업무 전용 역할을 배정할 필요가 없습니다. 신규 배포의 최종 결정은 **대상 부서장이 아닌 작성 부서장**이 담당합니다. 대상 부서의 업무분장 승인과 기존 인수인계 승인은 각각의 기존 절차를 따릅니다.

## 신규 작성부터 수행까지

1. **공통업무 · 지시사항 → 공통 세부업무 작성**을 엽니다.
2. 공통업무 또는 지시사항을 선택하고 세부업무 이름, 설명, 공통 마감일, 반복 주기, 필수 절차를 입력합니다. 사업명은 선택 입력이며, 지시사항은 지시자와 지시일자가 필요합니다.
3. 전체 부서 또는 지정 부서를 선택하고 **N개 부서 배포 승인 요청**을 누릅니다.
4. 작성자는 **작성·배포 승인**에서 대기 상태를 확인합니다. 이때 대상 부서의 접수·배정 목록에는 아직 새 업무가 생기지 않습니다.
5. 작성 부서장은 **승인 대기 → 검토 및 승인**에서 요청 당시 내용, 대상 부서, 절차를 검토하고 **승인하여 부서에 배포**를 누릅니다.
6. 승인되면 대상 부서에 접수되고 부서 담당자에게 앱 내 알림이 생성됩니다. 대상 부서에는 활성 부서 담당자와 부서장이 있어야 합니다.
7. 대상 부서의 부서 담당자가 팀에 배부하고, 해당 팀장이 업무 담당자를 지정합니다.
8. 업무 담당자가 **내 단위업무에 등록**하여 수행합니다. 기존 관련 근거·절차·일정·월별 실적 흐름을 이용합니다.

부서 업무분장이 확정되어 있어도 새 업무를 접수할 수 있습니다. 다만 팀·개인 배정과 내 단위업무 등록은 기존 재작성 허용 조건을 따릅니다. 이 기능은 [개선 로드맵 3-C](IMPROVEMENT-ROADMAP.md)의 ‘확정 부서에서 신규 업무의 변경분만 별도 승인’ 구현을 포함하지 않습니다.

## 반려와 보완 재요청

1. 작성 부서장은 검토 모달에 반려 사유를 입력하고 **반려**를 누릅니다. 빈 사유로는 반려할 수 없습니다.
2. 최초 배포가 반려되면 대상 부서에는 배포되지 않습니다. 작성자는 **반려** 탭에서 사유를 확인합니다.
3. 최신 반려 건의 **보완 후 재요청**을 눌러 업무 내용·절차·대상 부서 등을 고칩니다. 관리자도 반려된 최초 요청의 보완을 지원할 수 있습니다.
4. 다시 요청하면 새 승인 대기 이력이 생성됩니다. 이전 요청과 반려 사유는 보존됩니다.
5. 작성 부서장이 새 요청을 검토합니다. 이전 요청을 다시 승인하거나 이미 처리한 요청을 중복 처리할 수 없습니다.

승인 대기 중인 요청의 기준 정보를 바꾸거나 같은 업무에 배포 요청을 중복 생성할 수 없습니다. 승인 시점에 작성자 자격·소속, 업무 기준 버전, 요청 당시 총괄 담당자, 대상 부서 상태가 달라졌다면 적용을 거절합니다. 현재 책임과 요청 내용을 확인하고 필요한 보완 절차를 진행합니다.

## 대상 부서 추가

1. 배포된 업무의 **대상 부서 추가**를 누릅니다. 작성자·관리자 또는 기존 장·차관 지시사항 관리 범위의 기획팀이 요청할 수 있습니다.
2. 아직 배포하지 않은 부서를 선택하고 **N개 부서 추가 승인 요청**을 누릅니다.
3. 작성 부서장이 추가할 부서를 검토하여 승인합니다. 승인 전에 새 부서에는 업무가 접수되지 않습니다.
4. 승인 후 새 부서의 부서 담당자가 배부를 시작합니다. 이미 배포된 부서의 팀·담당자·단위업무 연결과 수행 기록은 유지됩니다.
5. 추가 요청이 반려되어도 기존 배포는 유지됩니다. 사유를 확인하고 대상 부서를 다시 선택하여 새 추가 요청을 만들 수 있습니다.

최초 요청의 **보완 후 재요청**은 미배포 상태에서 내용을 고치는 기능입니다. 이미 배포된 업무의 추가 요청이 반려된 경우에는 **대상 부서 추가**를 다시 사용합니다.

## 조회 범위와 기록

- 작성자, 작성 부서의 부서장·부서 담당자, 관리자는 승인 전 요청과 처리 이력을 확인할 수 있습니다.
- 대상 부서는 승인된 배포를 기준으로 업무를 받습니다. 다른 부서의 미승인·반려 요청은 대상 부서라는 이유만으로 조회되지 않습니다.
- 요청에는 요청자·시각·작성 부서·대상 부서·업무 기준 버전·당시 내용이 남습니다. 처리 후에는 승인 또는 반려 상태, 처리자·시각·의견이 남습니다.
- 요청·승인·반려·재요청·추가 배포 명령은 감사 이력에 기록되며, 요청자와 담당자에게 앱 내 처리 알림을 생성합니다.
- 관리자는 현황을 조회하거나 요청을 지원할 수 있지만 부서장의 승인 권한을 얻지는 않습니다. 작성자 본인이나 다른 부서장이 자신의 역할만으로 승인할 수 없습니다.

## 기존 데이터 호환

| 기존 데이터 | 적용 방식 |
| --- | --- |
| 사용자에 남아 있는 `commonTaskPermission` | 구형 JSON을 읽기 위한 선택 필드로 수용하며 권한 판단에는 사용하지 않음. 기존 사용자·업무를 삭제하거나 초기화하지 않음 |
| `member` 역할 | 내부 역할 코드는 유지하며 화면 표시를 업무 담당자로 변경 |
| 승인 정보가 없는 기존 공통업무 | 이미 배포된 업무로 계속 취급. 화면에는 **기존 등록 업무**로 표시하며 과거 부서장 승인이 있었다고 소급 기록하지 않음 |
| 기존 배포·배정·등록·수행 기록 | 그대로 유지. 신규 승인 모델 때문에 담당자나 회차를 다시 만들지 않음 |
| 기존 업무의 추가 부서 배포 | 새 추가 요청부터 작성 부서장 승인 적용. 원래 작성 부서가 없는 구형 건은 현재 총괄 담당자의 부서를 기준으로 요청 부서를 정해 보존 |
| 기존 공통업무 총괄 역할 인수인계 | 별도 공통업무 권한 없이 해당 부서의 활성 업무 담당자·팀장·부서 담당자·관리자 중 후임 선택. 기존 인수인계의 부서장 승인 절차 유지 |

`originDepartmentId`, `publicationStatus`, `approvalRequests`는 기존 공통업무에 없는 경우도 읽을 수 있는 선택 필드입니다. 신규 요청부터 작성 부서와 승인 정보를 저장하므로 기존 Neon 워크스페이스를 재시드할 필요가 없습니다.
