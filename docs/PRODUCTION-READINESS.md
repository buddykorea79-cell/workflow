# 온이음 운영 전환 검토 기록

> **현재 프로젝트의 목표는 프로토타입 개발입니다.** 이 문서는 초기 운영 전환 검토 이력으로 보존합니다. 이후 추가된 프로토타입 로그인·Neon 파일 저장·데이터 이관 기능을 포함한 실제 설정은 **[프로토타입 Neon 설정 안내](PROTOTYPE-NEON-SETUP.md)**를 따릅니다. 아래의 구현 상태는 작성 당시 기준이며 현재 진행할 필수 작업 목록이 아닙니다.

> **현재 역할·공통업무 흐름:** 역할은 업무 담당자·팀장·부서 담당자·부서장·관리자 5개이며, 별도의 공통업무 담당 권한은 폐지했습니다. 부서장을 제외한 활성 구성원이 세부업무를 작성하고, 작성 부서장이 승인하면 지정 부서에 등록됩니다. 대상 부서의 부서 담당자가 배부합니다. 승인·반려·재요청·추가 배포와 기존 데이터 호환은 [공통업무 배포 승인 QA](QA-common-publication.md)를 참고합니다. 아래 과거 운영 검토 이력은 유지하며, 역할·권한 명칭과 해당 흐름만 현재 기준으로 안내합니다.

기준일: 2026-11-01. 현재 저장소의 실행 코드와 공식 공급자 문서를 기준으로 작성했습니다. 이 문서는 준비 계획이며 Neon 프로젝트 생성, 실제 인증 연동, 운영 배포 또는 복구 시험 완료를 뜻하지 않습니다.

**현재 앱은 로컬 시연용입니다. Neon 저장 어댑터는 있지만 DB 주소만 입력해서 바로 기관용 서비스를 시작할 수는 없습니다. 실제 로그인, 운영 초기 데이터, 첨부 저장소와 검증이 먼저 필요합니다.**

서비스 요금제는 동시 사용자, 첨부 용량, AI 사용량과 복구 보존기간을 확인한 뒤 선택합니다. 이 문서는 유료 가입이나 특정 요금제를 확정하지 않습니다.

## 3. Neon DB 연결 순서

### 연결과 초기화

1. 검증용 Neon 환경과 운영 환경을 분리합니다. 검증 앱이 운영 DB·인증·파일 저장소를 공유하지 않도록 환경변수를 따로 관리합니다.
2. 앱용 DB 계정과 마이그레이션용 계정을 분리합니다. 앱에는 필요한 조회·수정 권한만 부여하고, 스키마 변경 권한은 배포 관리 계정이 가집니다.
3. 앱의 `DATABASE_URL`에는 TLS가 적용된 연결 문자열을 설정합니다. 서버리스 환경은 Neon 콘솔에서 제공하는 pooled 연결을 우선 검토하고 실제 트랜잭션 흐름을 시험합니다. pooled 주소는 호스트에 `-pooler`가 포함됩니다. [Neon 연결 풀 공식 문서](https://neon.com/docs/connect/connection-pooling)
4. `drizzle/0001_workspace.sql`을 마이그레이션 계정으로 적용합니다. 이 SQL은 테이블만 만들며 사용자·업무 데이터는 넣지 않습니다.
5. `IEUM_WORKSPACE_ID`와 같은 ID의 `ieum_workspaces` 행을 초기화합니다. 이 행이 없으면 앱은 `DATABASE_NOT_INITIALIZED`로 실패합니다.
6. 검증용 가상 데이터와 운영용 실제 조직 초기화를 분리합니다. 현재 `scripts/setup-neon.ts`는 가상 조직·업무를 넣는 개발용 스크립트이며, `.data/workspace.json`을 옮기는 도구가 아닙니다.
7. 연결·읽기·쓰기·동시 저장 충돌·서버 재시작 후 영속성을 확인한 뒤 인증/파일 시험으로 넘어갑니다.

검증용 브랜치에서만 실행할 수 있는 현재 명령은 다음과 같습니다. `DATABASE_URL`과 `IEUM_WORKSPACE_ID`를 해당 프로세스 환경에 먼저 안전하게 설정해야 합니다. 스크립트 자체는 `.env.local`을 자동으로 읽지 않습니다.

```powershell
# 대상 DB가 검증용인지 먼저 확인한 후 실행
$env:IEUM_WORKSPACE_ID = 'staging'
$env:IEUM_ALLOW_DEMO_SEED = 'true'
try {
  npx tsx scripts/setup-neon.ts
} finally {
  Remove-Item Env:IEUM_ALLOW_DEMO_SEED -ErrorAction SilentlyContinue
}
```

스크립트는 트랜잭션 안에서 SQL과 초기 데이터를 적용하며, 같은 ID가 이미 있으면 `ON CONFLICT DO NOTHING`으로 보존합니다. **기존 JSON 데이터를 갱신하거나 새 필드를 이관하는 버전별 데이터 마이그레이션 기능은 없습니다.** `drizzle-kit`이나 `npm run db:migrate` 명령도 현재 설치·등록되어 있지 않습니다.

### 운영 데이터와 확장

- 운영용 빈 워크스페이스 생성 및 실제 부서·사용자 초기화 도구를 별도로 작성합니다. 사용자 ID와 5개 조직 역할, 작성 부서장의 공통업무 배포 승인과 대상 부서의 배부 권한을 검수합니다.
- 로컬 데이터를 옮길 경우 별도 가져오기 도구로 스키마 검증, ID·참조·revision 보존, 중복 방지, 건수 대조를 수행합니다. 첨부 원본은 DB JSON과 별도로 이관합니다.
- JSONB 한 행을 매 요청 잠그므로 같은 워크스페이스의 읽기/쓰기가 경합할 수 있습니다. 실제 업무량으로 응답시간과 잠금 대기를 측정하고, 허용된 규모의 파일럿만 운영합니다.
- 기관 규모 확장 전 사용자·부서·업무·회차·절차 결과·성과·평가·첨부·감사를 분리하고 외래키, 고유 제약, 인덱스와 DB 접근 경계를 정의합니다. 현재 SQL에는 RLS가 없으며 서버의 업무 권한 검사가 주된 접근 통제입니다.
- 현재 `IEUM_WORKSPACE_ID`는 서버 전체 설정입니다. 기관별 워크스페이스 선택이나 다기관 테넌트 라우팅은 구현되어 있지 않습니다.

## 4. 실제 로그인과 권한 연결

현재 `src/lib/auth.ts`는 인증 서버의 `get-session`에 쿠키를 전달하고, 받은 외부 사용자 ID를 `NEON_AUTH_USER_MAP`으로 내부 사용자 ID에 매핑합니다. 설정 누락은 `AUTH_NOT_CONFIGURED`, 미등록 사용자는 `INVITATION_REQUIRED`로 거절합니다. 그러나 로그인 페이지·인증 콜백·운영 로그아웃을 만드는 인증 SDK/경로는 아직 없습니다. 현재 화면의 로그인·로그아웃·역할 전환은 모두 데모용 `/api/session`을 호출하며 비로컬 환경에서는 차단됩니다.

- [ ] Neon Auth를 선택하면 현재 공식 Next.js 연동 절차에 맞춰 로그인/로그아웃·세션 갱신·쿠키 전달을 구현합니다. 현재 수기 어댑터가 공급자의 현재 응답·쿠키 규칙과 맞는지도 검증합니다. [Neon 인증 공식 문서](https://neon.com/docs/auth/overview)
- [ ] 기관 SSO가 필수라면 지원 프로토콜·기관 인증 정책을 확인하고 별도 연동 범위를 정합니다. Neon DB 사용이 Neon Auth 사용을 강제하지는 않지만 현재 코드는 Neon 인증 어댑터를 전제로 합니다.
- [ ] 운영 도메인을 신뢰 도메인에 등록하고, 사용하는 이메일/OAuth 공급자 설정과 기관 초대 정책을 완료합니다. Neon은 운영 전 자체 메일 공급자·OAuth 자격증명 및 localhost 허용 설정 검토를 안내합니다. [Neon 인증 운영 체크리스트](https://neon.com/docs/auth/production-checklist)
- [ ] 외부 인증 ID와 내부 사용자 ID를 연결합니다. 현재 환경변수 매핑의 예시 구조는 `{"external-auth-user-id":"internal-user-id"}`입니다. 운영에서는 이를 DB의 고유 매핑과 관리 이력으로 옮겨 추가·권한 변경·퇴직 처리를 배포 없이 수행할 수 있게 합니다.
- [ ] 인증에 성공해도 내부 사용자의 활성 여부·소속·역할을 다시 확인합니다. 퇴직/전보/권한 회수 후 기존 세션의 접근 차단을 시험합니다.
- [ ] 운영 화면에서 데모 계정 선택·역할 전환을 제거하고 사용 안내의 로컬 시연 설명을 실제 로그인 방식과 구분합니다.

`NODE_ENV=production`이나 `npm start`만으로 데모 로그인이 비활성화되지는 않습니다. 현재 판단 조건은 Vercel 여부, `NEON_AUTH_BASE_URL` 설정과 요청 호스트입니다. 자체 서버를 운영할 때도 인증 설정과 외부 요청 동작을 반드시 확인해야 합니다.

## 5. 첨부 저장소와 본문 추출

현재 `/api/attachments`는 비로컬 환경에서 `DIRECT_STORAGE_REQUIRED`로 업로드를 거절합니다. `/api/procedure-extract`도 비로컬 환경에서 `LOCAL_EXTRACTION_ONLY`를 반환합니다. 따라서 저장소 계정 생성만으로 운영 업로드나 PDF 분석이 활성화되지는 않습니다.

필요한 구현 순서는 다음과 같습니다.

1. 서버가 로그인·업무 권한·파일 크기·종류를 검사하고 제한된 업로드 권한을 발급합니다.
2. 브라우저가 비공개 저장소로 직접 업로드합니다. 객체 경로는 서버가 정하고 임의 덮어쓰기를 허용하지 않습니다.
3. 서버가 저장된 객체의 크기·형식·해시를 확인하고 업로드 세션을 최종화합니다. DB 저장 실패, 미완료 파일과 재시도를 처리합니다.
4. 악성 파일 검사 작업이 격리/통과/거절 상태를 갱신합니다. 현재 관리자의 `test_allowed`는 개발용 출처 확인이며 악성코드 검사 통과가 아닙니다.
5. 다운로드 시점마다 현재 업무 권한과 검사 상태를 확인하고 짧은 유효기간의 접근을 발급합니다. 퇴직·이관·권한 회수 후 접근을 다시 확인합니다.
6. PDF 본문 추출은 검사 통과한 저장 객체를 대상으로 별도 작업에서 수행합니다. 대용량·스캔 PDF의 OCR 필요 여부와 지원 형식을 정합니다. 미지원 파일은 본문 직접 입력 안내를 제공합니다.

Vercel Function의 요청/응답 본문 한도는 공식 문서 기준 4.5MB이므로 현재 10MB 파일을 함수로 직접 중계하는 방식과 맞지 않습니다. 직접 저장소 업로드·다운로드가 필요하며, 커진 워크스페이스 JSON 응답도 같은 한도를 고려해야 합니다. [Vercel Functions 제한](https://vercel.com/docs/functions/limitations)

## 6. 환경변수 관리

비밀값은 호스팅의 서버 환경변수 또는 로컬의 Git 제외 파일에만 저장합니다. `.env.example`에는 빈 값/설명만 둡니다. 아래 값에 `NEXT_PUBLIC_`을 붙이지 않습니다.

| 이름 | 현재 용도 | 운영 설정 |
| --- | --- | --- |
| `DATABASE_URL` | Neon 연결. 존재하면 로컬 JSON 대신 DB 사용 | 필수. 환경별로 분리하고 DB 비밀번호 회전 절차 마련 |
| `IEUM_WORKSPACE_ID` | 조회·저장할 워크스페이스 행 ID. 기본 `development` | 검증/운영 ID를 명시하고 실제 초기화 행과 일치시킴 |
| `NEON_AUTH_BASE_URL` | 인증 `get-session`의 HTTPS 기준 주소 | 현재 인증 어댑터 사용 시 필수. 공급자 콘솔의 실제 주소 사용 |
| `NEON_AUTH_USER_MAP` | 외부 인증 ID → 내부 사용자 ID JSON | 현재 어댑터의 임시 필수 설정. 운영 사용자 관리 테이블로 전환 필요 |
| `IEUM_APP_ORIGIN` | 변경 요청의 동일 출처 검사 기준 | 실제 운영 HTTPS origin을 정확히 지정 |
| `IEUM_SESSION_SECRET` | 로컬 데모 세션 HMAC 서명 | 데모 세션용이며 Neon 인증 시크릿을 대체하지 않음. 운영 인증 SDK가 요구하는 별도 시크릿은 연동 때 추가 |
| `IEUM_DATA_DIR` | 로컬 JSON·첨부 저장 위치 | 로컬 시연/테스트용. Neon 객체 저장소 경로를 지정하는 값이 아님 |
| `IEUM_ALLOW_DEMO_SEED` | 개발용 DB 초기화 허용 | 운영에서 비활성. 검증 초기화 명령 실행 때만 `true` |
| `BIZROUTER_API_KEY` | 서버 측 AI API 인증 | AI 사용 시 필수. 프로젝트별 키·사용량 한도 설정 |
| `BIZROUTER_MODEL` | 허용 목록의 구체 모델 ID | `json_schema` 지원을 확인한 실제 ID 지정 |
| `LAW_API_OC` | 법령 연동용 예약 설정 | 현재 이 값만 넣어서는 법령 연동되지 않음. 어댑터 추가 개발 필요 |

외부 인증 SDK, 객체 저장소, 검사 작업, 모니터링용 환경변수는 해당 연동을 구현하면서 추가해야 합니다. 현재 코드에 없는 변수를 임의로 설정해도 기능은 생기지 않습니다.

공개 저장소 반영 준비 중 예시 환경파일에서 비밀키 값을 발견해 Git 제외 로컬 파일로 분리했습니다. 이 키는 공급자 콘솔에서 폐기·재발급하고 새 값으로 교체하는 것이 필요합니다. 이 문서에는 키 값이 없으며, 키 회전 자체를 완료했다는 뜻은 아닙니다.

## 7. BizRouter 운영 준비

- [ ] 현재 예시 파일에 있었던 키를 회전하고 새 프로젝트 키를 서버 환경에 등록합니다.
- [ ] 공급자의 모델 목록에서 구조화 응답을 지원하는 허용 모델 ID를 선택합니다. 코드가 요청마다 목록과 `json_schema` 지원을 확인합니다. [BizRouter 모델 목록](https://bizrouter.ai/docs/models), [구조화 응답](https://bizrouter.ai/docs/chat-completions)
- [ ] 비민감 근거로 실제 생성·인용 검증·초안 적용·절차도 표시까지 시험합니다. 현재 코드는 선택 근거 1~20개, 본문 합계 60,000자, 호출 60초 제한이며 API 경로의 `maxDuration`은 70초입니다. 배포 실행시간이 이를 수용하는지 확인합니다.
- [ ] 사용자/부서별 요청 한도, 월 예산, 비용·오류 알림을 정합니다. 현재 진행 중 요청 제한은 프로세스 메모리 `Set`이므로 여러 인스턴스 전체의 중복 호출을 막지 못합니다.
- [ ] 긴 작업의 결과 보존, 재시도 정책, 취소·중복 생성 방지와 사용량 기록을 구현합니다. 자동 재시도가 이중 과금/중복 적용으로 이어지지 않도록 합니다.
- [ ] 전송 범위를 기관 정책에 맞게 정합니다. 현재는 업무 제목·설명과 선택한 근거의 종류·제목·본문을 전송하며 첨부 원본·원문 URL을 가져오지 않습니다. 이 새 경로의 `TaskReference`에는 별도 기밀 분류나 AI 전송 동의 필드가 없으므로 실제 기관 자료에 적용할 통제를 추가해야 합니다.
- [ ] AI 결과를 검토할 초안으로 유지하고 원문 인용·담당 역할·선행 관계·완료 조건을 사용자가 확인하게 합니다. 법령의 최신성이나 법적 적용 판단은 현재 자동 검증 범위가 아닙니다.

## 8. 배포, CI와 복구

### 배포 방식

Vercel을 선택하면 저장소를 연결하고 검증/운영 환경변수를 분리한 뒤 Next.js 빌드를 실행합니다. 현재 API는 Node.js 런타임을 사용하므로 정적 파일 호스팅만으로는 운영할 수 없습니다. Preview에도 운영 DB·인증 키·첨부 저장소를 그대로 연결하지 않습니다.

자체 서버를 선택하면 지원되는 Node.js 버전을 고정하고 다음 빌드 명령을 사용합니다.

```text
npm ci
npm run typecheck
npm test
npm run build
```

현재 `npm start`는 `127.0.0.1`에만 바인딩하므로 같은 호스트의 역방향 프록시 뒤에서 사용할 수 있습니다. 컨테이너/PaaS에서 외부 포트 바인딩이 필요하면 배포 시작 명령을 명시적으로 `npx next start --hostname 0.0.0.0 --port <플랫폼 포트>`로 구성하고 인바운드는 프록시/플랫폼으로 제한합니다. `Start-Ieum.cmd`는 로컬 실행 편의 도구입니다. Next.js는 자체 호스팅 시 역방향 프록시 사용을 권장합니다. [Next.js 자체 호스팅](https://nextjs.org/docs/app/guides/self-hosting)

- [ ] 도메인·HTTPS·DNS·보안 헤더를 설정하고 인증 쿠키/리다이렉트/동일 출처 검사를 검증합니다.
- [ ] 현재 저장소에는 자동 CI 워크플로가 없습니다. GitHub Actions 등에 설치 → 타입 검사 → 테스트 → 빌드 단계를 추가하고 실패 시 배포를 막습니다. 실제 실행 결과와 브랜치 보호의 필수 검사 설정까지 확인합니다.
- [ ] DB 마이그레이션은 배포 요청마다 실행하지 않고 명시적 배포 단계에서 수행합니다. 운영 데이터와 구버전 코드의 호환성을 유지합니다.
- [ ] 상태 확인 경로, 오류·지연·DB 잠금·인증 실패·AI 사용량 관측과 장애 알림을 추가합니다. 현재 `apiError`의 기본 로그만으로는 원인 추적이 부족하므로 요청 ID와 안전한 오류 맥락을 기록하되 쿠키·키·업무 본문은 로그에서 제외합니다.
- [ ] 코드 롤백과 데이터 복구를 구분합니다. 관리자 메뉴의 버전 기록은 배포/롤백 도구가 아닙니다.

### 백업과 복구

- [ ] 허용 데이터 손실 시간(RPO), 복구 목표 시간(RTO), 보존기간을 업무 담당자와 정합니다.
- [ ] Neon 복구 이력 보존기간을 실제 요금제에서 확인하고 필요 시 별도 암호화 백업을 구성합니다. 복구 가능한 브랜치와 이력 범위를 확인하고 DB 복구를 시험합니다. 인증 스키마를 포함한 DB 상태와 외부 객체 저장소는 별도로 복구해야 합니다. [Neon 시점 복구](https://neon.com/docs/postgres/backup-restore/branch-restore)
- [ ] DB와 첨부의 일관된 백업 기준을 정의합니다. 파일 버전·객체 ID·해시를 복구한 DB 메타데이터와 대조합니다.
- [ ] 검증 환경에서 복구 후 사용자 로그인, 권한, 업무·회차·성과·평가·감사 이력, 첨부 다운로드를 시험하고 실제 복구 시간을 기록합니다.
- [ ] 운영 원본 데이터를 복제한 검증 환경에는 같은 접근 통제를 적용하고, 필요하면 가명/가상 데이터로 바꿉니다.

## 9. 실행 우선순위와 서비스 개시 기준

| 순서 | 할 일 | 완료 판단 |
| --- | --- | --- |
| 1 | 키 회전, 운영 도메인·호스팅·리전·파일럿 인원 결정 | 비밀값 Git 제외, 공급자 설정 담당자와 서비스 범위 확정 |
| 2 | 검증 Neon DB 및 운영 초기화 도구 | 재시작 후 데이터 보존, 기존 데이터 보존·마이그레이션 시험 |
| 3 | 실제 로그인과 사용자/권한 연결 | 실제 계정 로그인·로그아웃, 미초대·타부서·퇴직 사용자 차단 |
| 4 | 비공개 파일 저장·검사·본문 추출 | 10MB 파일 업로드/다운로드, 실패 복구, 권한 회수와 격리 검증 |
| 5 | BizRouter 실연동과 예산·자료 정책 | 실제 생성·인용·시간초과·키 오류·한도 초과 처리 확인 |
| 6 | CI·HTTPS·관측·백업/복구 | 배포 성공, 이전 코드 복원, DB/파일 복구 시험 기록 |
| 7 | 제한된 인원으로 파일럿 | 아래 업무 시나리오와 동시성·응답시간 기준 충족 |
| 8 | 기관 규모 확장 | 정규화·DB 경계·부하·운영 책임과 필요한 추가 연동 완료 |

파일럿 전에는 업무 담당자, 팀장, 부서 담당자, 부서장, 관리자 5개 역할의 실제 계정으로 다음 흐름을 확인합니다. 별도의 공통업무 담당 계정이나 추가 권한은 만들지 않습니다.

- 공통 세부업무 작성 → 작성 부서장 배포 승인 → 대상 부서 담당자의 팀 배부 → 팀장의 업무 담당자 배정 → 내 업무 등록 → 관련 근거 작성 → AI 초안 검토 → 절차/일정 저장 → 완료 → 새 회차 등록.
- 지시사항의 월별 실적 입력과 기획팀 통합 관리, 다른 부서 세부업무/성과의 접근 제한.
- 업무분장 확정/재작성과 잠금, 수행 기록의 허용 범위.
- 성과 저장 → 단위업무 비중 합계 50점 → 제출 → 회수/평가 확정과 이후 수정 제한.
- 동일 업무 동시 수정·중복 요청·인증 만료·DB 장애·업로드 실패 후 데이터 보존.

외부 알림, 법령 자동 수집, 정시 반복 작업, 조직개편 일괄 이관과 별도 인수인계 메뉴 통합은 서비스 범위에 따라 후속 개발로 관리합니다.
