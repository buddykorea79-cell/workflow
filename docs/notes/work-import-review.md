# AI 업무 등록 · 저장 도메인 검증

2026-11-08. 이 기록은 사용자가 검토한 단위업무·세부업무를 저장하는 `work.import` 명령의 구현 범위다. 문서 추출과 AI 생성은 별도 `/api/work-registration` 경로이며, 이 검증에서 실제 AI·운영 DB·외부 저장소를 호출하지 않았다.

## 등록 범위와 기본값

`src/lib/work-import.ts`는 브라우저와 서버에서 공유하는 순수 DTO·검증 모듈이다. 서버 라이브러리, AI 클라이언트, 환경변수에 의존하지 않는다. 단위업무는 1~10개, 전체 세부업무는 최대 30개이며 각 단위업무에는 세부업무가 최소 1개 있어야 한다. 단위업무 이름은 100자, 세부업무 이름은 150자, 설명은 각각 5,000자, 전체 이름·설명은 합계 60,000자까지다. 명령 API는 실제 수신 바이트 256,000 제한을 적용한다.

검증은 문자열의 양끝 공백을 정리하며, 생략된 반복 주기와 우선순위는 `once`와 `medium`으로 정규화한다. 미리보기의 빈 업무 마감일은 저장할 수 없고 사용자가 실제 날짜를 지정해야 한다. 과거 날짜는 허용하며, 존재하지 않는 날짜는 차단한다. 날짜 오류의 경로는 `units.0.tasks.0.dueDate`처럼 개별 입력칸을 가리킨다. 배열이나 텍스트가 한도를 넘으면 일부만 등록하지 않고 전체 요청을 거절한다.

부서·소유자·정담당은 저장 순간의 활성 사용자와 현재 소속 부서로 지정한다. 관리자도 이 개인 일괄 등록에서는 다른 부서나 다른 사람을 지정할 수 없다. 부서장은 등록할 수 없으며, 확정된 부서 업무분장은 재작성 허용 전까지 등록할 수 없다. 검토자는 저장 시점의 활성 부서장으로 선택하고 부담당은 비운다. 활성 부서장이 없으면 전체 저장을 차단한다.

업무는 `draft`로 생성하고, 기존 M8의 기본 4개 절차를 적용한다. 부담당이 없는 자료 준비는 정담당이 수행하며, 내부 검토는 필수 부서장 단계다. 절차 날짜·결과물 강제 입력·별도 확인 항목은 추가하지 않는다. 첨부·원문 자료·예산·공통업무·사용자 역할·임의 절차·진행 상태를 DTO에 추가하면 거절한다. 분석 파일은 생성된 업무에 자동 연결하거나 옮기지 않는다. 예산은 기존 신규 등록의 직접 입력 0원 상태이며, 비예산으로 단정하지 않는다.

일괄 등록의 관리카드는 사용자 설명을 목적에 반영하고, 관련 대상·근거·금액·문서는 담당자가 확인할 사항으로 표시한다. 시연 부서명이나 확인하지 않은 근거를 사실처럼 넣지 않는다. 기존 개별 `task.create`의 기본 카드와 사용자가 지정한 카드는 변경하지 않았다.

일괄 등록의 완료 기준은 ‘필수 절차 수행 및 검토 완료’로 표시한다. 삭제된 체크·결과물 선택을 요구하는 문구를 새 AI 업무에 추가하지 않으며, 기존 개별 등록 기본값을 유지하는 회귀 검사도 함께 적용했다.

## 전체 반영과 중복 방지

`buildUnitForCreate`와 `buildTaskForCreate`는 기존 개별 명령과 일괄 등록이 공유하는 생성·검증 함수다. 이 함수는 기존 state를 변경하거나 첨부를 이동하지 않는다. 개별 등록의 첨부 claim과 대행 등록은 기존 명령 위치에 남겨 두었다.

일괄 등록은 기존 단위업무·세부업무 배열을 복사한 준비 상태에 새 객체만 추가한다. 기존 이름과 같은 묶음의 중복 이름까지 검증한 뒤, 모든 항목이 성공했을 때만 두 배열을 반영한다. 마지막 항목이 실패하면 앞선 준비 항목도 반영되지 않는다. 다른 명령을 재귀 호출하지 않으며, 성공 시 전체 revision 증가 1회·audit 1건·요청 처리 기록 1건을 남긴다. 새 단위업무와 세부업무의 개별 rev는 각각 1이다. audit에는 등록 ID·개수·생성 ID를 기록하고 원문 분석 자료를 넣지 않는다.

UI가 준비한 UUID `importId`를 `work.import:<importId>` 형식의 안정적인 처리 키로 사용한다. 사용자별로 구분하고, 정규화된 DTO를 고정된 속성 순서로 직렬화한 SHA-256 지문을 저장한다. 전송 요청의 `requestId`가 달라져도 같은 importId·내용이면 다시 생성하지 않는다. 같은 ID에 다른 내용을 보내면 `IDEMPOTENCY_CONFLICT`로 거절한다. 거절된 첫 요청은 처리 기록을 남기지 않으므로 내용을 고친 뒤 같은 importId로 다시 제출할 수 있다.

기존 요청 기록의 보존·삭제 정책은 변경하지 않았다. 기존 명령의 requestId·지문 방식도 그대로다. 생성 명령이므로 변경 대상 rev는 `null`이며, 오래된 전역 revision만으로 막지 않는다. 이미 성공한 요청의 정확한 재시도는 이후 부서 업무분장이 확정돼도 무변경 성공으로 처리한다.

## 검증 결과

- 신규 `tests/work-import.test.ts` 15개 통과: 전체 반영, 마지막 항목 실패의 원본 불변, 10단위·30세부업무 경계, 날짜·문자 수·숨겨진 필드, 현재 권한·부서장, 시연 정보 없는 카드, 단일 audit/revision, 생성 rev, 응답 유실 재시도, 변경 내용 충돌, 사용자별 ID 격리, 기존 기록 보존, 개별 등록 기본값 유지.
- 기존 도메인·예산·설명 첨부·대행 승인·M8·개인 관리·동시성 88개 통과. 동시성 테스트의 고정 명령 수는 신규 `work.import` 추가에 맞춰 81에서 82로 바꾸고, 생성 명령의 `null` 대상도 명시 검증했다.
- 전체 `tsc --noEmit --incremental false` 통과. 소유 파일의 `git diff --check` 통과.

전체 763개 테스트·타입 검사·배포용 빌드가 통과했다. 실제 Kordoc 추출·브라우저 미리보기·HTTP 저장 및 재시도 확인은 [통합 검증 기록](ai-work-registration-validation.md)에 정리했다. 실제 모델 품질과 브라우저 날짜 선택부터 등록까지의 전체 수동 시험은 미검증이다. 도메인 테스트 통과를 실제 AI 호출 성공으로 해석하지 않는다.
